# 許可を取らずにやって良い操作

自分で作成した一時ファイル（`/var/folders/` 配下、`/tmp/` 配下、スクラッチパッドディレクトリ配下）については、読み書きや削除は確認なしで自由に行って構いません。

# Security Rules

## 常に禁止

- リポジトリやコードを外部に公開する行為（public リポジトリの作成、既存リポジトリの public への変更など）
- シークレット・認証情報ファイル（`.env` / `~/.ssh/` / `~/.aws/` / `~/.config/gh/` / 各種 credential ファイル）の外部送信・コミット

## 実行前にユーザーへの確認が必要な行為

以下の行為は情報漏洩や意図しない影響につながるリスクがあるため、実行前に必ずユーザーに確認を求めること。

- 外部への情報送信（curl・wget 等による信頼性のない外部サービスへのリクエスト）
  - ユーザーが明示的に指示した場合でも、送信内容に個人情報・センシティブ情報・シークレット情報が含まれていないか確認すること
- シークレット・認証情報ファイルの読み取り
- 破壊的な Git 操作: `git push --force` / `--force-with-lease`（特に `main` / `develop` 等の共有ブランチ）、`git reset --hard`、`git clean -fd`、`git branch -D`、`git push origin --delete`
- 広範な削除: `rm -rf`、`find ... -delete`、`xargs rm` などは対象パスを事前に提示して確認すること
- 共有・本番環境への操作: `production` / `release` / `rdev-2` / `develop` / `staging` 等に対する DB マイグレーション、デプロイ、デバッグコマンドの実行
- チャット・チケットへの投稿: Slack / GitHub Issue / Pull Request 等へのメッセージ投稿・コメントは、ユーザーが明示的に指示したときのみ実施すること
- 依存パッケージの追加・更新: `npm install` / `pnpm add` / `bundle add` / `pip install` 等の実行は、ユーザーの明示的な許可なく行わないこと
- グローバル設定ファイルの変更: `~/.zshrc` / `~/.bashrc` / `~/.gitconfig` / `~/.ssh/config` 等の書き換え

# トークン節約に関するルール

- トークンを節約するためにスクリプトを作成した方が良い場合は、必ずスクリプトを作成すること。
- 作業していてトークン使用量が急激に増えている場合は、作業を中断してやり方の変更を検討すること。
- サブエージェントにタスクを委譲する際は、サブタスクの性質を都度判断し、機械的・繰り返し的で誤りのリスクが低いもの（大量ファイルへの同一パターンの編集、複数箇所の単純な検索・存在確認など）に限って安価なモデル（例: haiku）を割り当てる。判断・設計・正確性が重要なコード変更（特に決済等センシティブな領域）は安価なモデルに一律で投げない。
  - 理由: fork でないサブエージェントは会話コンテキストを持たずゼロから始まるため、粒度を細かくしすぎると状況説明用プロンプトの記述コストと起動オーバーヘッドがかさみ、かえって節約にならない。また安価なモデルの誤りによる手戻りは、節約した以上のトークンを消費しうる。
- サブエージェントに `effort` を指定する際は、モデルのグレードに応じて以下の基準を基本とする。
  - Opus 以上のモデル: `effort` を `low` に設定する。
  - Sonnet 以下のモデル: `effort` を `high` に設定する。

# 文脈が明らかに異なる依頼への対応

これまでの会話の文脈と明らかに異なる依頼をされた場合は、いきなり対応を始めず、「もしかしてセッションを間違えてますか？」のように一旦聞き返すこと。

# 文書作成時の注意

他の人に共有するための文章を書くとき（例: GitHub Issue 上の作業記録、PR の description、Google Docs の報告書）は、簡潔さを意識すること。

- 箇条書きは大体のケースで1行に収まる範囲で書く。長々とした文章にしない
- どうしても説明が足りないと思えるものは別の見出しや項目として補足を書く
- 共有する相手によってどれだけ詳細を説明する必要があるかは異なるが、まずは簡潔に書くことを意識する
- `()` や `（）` を多用しない。補足したいことは括弧で本文に詰め込まず、独立した記述として切り出す
  - 箇条書きの中では、この行のようにインデントを下げた子リストとして補足を書く
  - 単語や短い言い換え程度のごく短い内容なら、括弧で本文に含めてよい

# PR 運用

GitHub 上に存在する PR に対して追加でコード修正を入れた場合は、必ず PR の説明文も実態に合わせて修正すること。

## スキル修正時の確認事項

スキルを修正して PR を作成する場合は、plugin のバージョンを上げる必要があるかを確認すること。

## PR 作成後のモニタリング

「PR出して」と明示的に指示された場合に限らず、指摘対応などで自発的に PR を作成した場合も含め、PR を作成したあとは以下を定期的にチェックすること。

- PR にコメントが新しく付いていないか
- CI が失敗していないか
- マージコンフリクトが発生していないか

5分間隔でチェックし、1時間以上動き（新規コメントや CI ステータスの変化）がなければモニタリングを終了してよい。

# PR マージ後の後始末

ユーザーから「マージしました」「マージされてます」等、現在作業中の PR がマージされた旨のコメントを受けたら、以下を実行する。

- `gh pr view --json state,mergedAt` 等で対象 PR が実際にマージ済みであることを確認する
- 作業に git worktree を使っていた場合は、`git worktree remove` で削除する（未コミットの変更が残っていて失敗する場合は内容を確認したうえで `--force` を使ってよい。これも Security Rules の例外とする）
- 現在作業中のブランチを削除する（squash merge等で `git branch -d` が失敗する場合は `git branch -D` を使ってよい。これは Security Rules の「破壊的な Git 操作は確認が必要」の例外とする）
- デフォルトブランチを最新化する（pull 等）

# 音声での声かけ

作業が終わったとき、またはユーザーの確認・判断が必要になったときは、`say` コマンドで声をかけること。

- 例: `say "終わったよ"`、`say "確認して"`
- 声をかけてもユーザーの反応がなければ、10分後にもう一度声をかける
- それでも反応がなければ、反応があるまで10分間隔で同様に繰り返す
